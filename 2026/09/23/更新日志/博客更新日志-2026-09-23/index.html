博客更新日志 — 2026年9月23日

这篇日志得从昨天说起——两天的活攒在一起才看得出是一条线：**把博客的视觉体系从”每个组件各写各的 CSS”，收成”一套语义变量 + 一套分流规则”**。

给 note 挂上角色名牌、把暗色配色从”逐角色维护”改成”统一底 + 角色描边”、给正文插图分两档外框、把 63 个手写 HTML 块换成标签、给 B站视频套一层天线小电视——单看都不相干，合起来就一句话：颜色只留一份定义，结构交给脚本判定，样式只认语义槽。

🏷️ 角色名牌：让 note 自己说出「谁在说话」（9月22日）

角色配色的 note 原先左上角是一枚图标圆标，认不出是哪个角色。这轮把它改成自适应宽度的名字吊牌。

定版视觉：底用主题表面色，角色色降级去当渐变描边和字色。

改动落三处：

  • _data/characters.yml：每角色加一个可选字段 label（吊牌显示文本，缺省回退 name）
  • scripts/colors.js：新增 after_post_render（优先级 20），把带角色 class 的 note 标成 <div class="note <角色> vw-role" data-role-label="名字">；同时补一个字色槽 --color-label-fg
  • source/css/custom.css：把主题原有的圆标伪元素改写成胶囊吊牌

一个不能渐变的东西怎么做出渐变描边

CSS 边框不能渐变，border-image 又不支持圆角——两个限制撞在一起，圆角胶囊配渐变描边看起来无解。解法是双层背景：

再配 2px solid transparent（透明 border 的宽度就是描边宽度），圆角和渐变就兼得了。

另外两个细节都是”少写一行就翻车”：

  • 名字文本走 content: attr(data-role-label)，角色名只存在于 characters.yml → 以后加角色零改 CSS/JS
  • ⚠ 必须写 font-family: inherit。不写会继承圆标的图标字体，名字直接渲染成方块

尺寸上有个耦合关系值得记：吊牌高度和 top 是一对——top = -高度/2，竖直中心恰好压在卡片上沿。所以调高度必须同步改 top，而且那个 top 得带 !important，否则被通用圆标规则（它的 top 带 !important，特异性压不过）盖掉。字号写 1em 而不是 14px 也是故意的：右下角有字号加减按钮会改 --global-font-size，用 em 才能跟着正文同步缩放。

配色不是审美问题，是对比度问题

一开始想”一个角色色做底、另一个角色色做字”，四个角色测下来全废：Kanade 1.5:1、Tsubasa 1.2:1、Ego 1.0:1、Aliena 1.7:1，最低的几乎等于没有对比（WCAG 小字底线是 4.5:1）。

原因很清楚：角色双色本来就是为渐变过渡挑的，明度天然相邻。所以名字这种纯文字必须跨明度配对。定版四角色实测 8.2 / 4.6 / 7.1 / 4.2:1。

一个被反复验证的痛点：**角色色实底牌贴在亮色主题的浅橙卡片上会”脏”**——两块暖浅色糊在一起。解药就是前面那句：牌子底改用主题表面色，角色色只留描边和字色。

🌗 暗色 note：角色色从「底」退到「描边」（9月22日）

暗色 mode 原先每个角色都要维护一套暗底色。这轮改成统一暗底 + 角色色渐变描边，维护量直接砍掉一整个维度。

底取 #1e1e1e——比父卡片 --card-bg（#121212）亮半档，保住卡片体量感。

动之前先查了一件事，结论决定了这活能不能干：--color-bg-a/b 这个变量全站唯一的消费者就是 note 底，改它不波及任何其他组件。影响面干净，才敢动。

一个先看见再决策的连带坑：吊牌底本来就是 --card-bg。如果 note 底也取 --card-bg，吊牌就和卡片同色，退化成”一枚只剩描边的空胶囊”。选了亮半档的暗底，吊牌反而天然比卡片暗半档——白赚一层层次。

🎨 亮色底板：四轮试错才摸到真问题（9月22日）

给角色底板做”降浓”这一件事，本小姐走了三轮弯路才踩到真问题上：

  1. 先按”更淡更干净”推 → 方向反了，底一淡就没了卡片存在感，和默认款差距过大
  2. 改成把两端钉在同一明度 → “怎么这几版都看不出双色？” 原因：默认款能看出渐变靠的不是色相，是两端 8–12 点的明度差；两端一样亮，双色自然消失
  3. 改成”中性底 + 渐变描边” → 又走偏，那压根不是想要的

第 4 轮才逼出真问题——渐变分量是按「垂直于渐变方向的 50% 分割线」算的，不按角度。卡片长宽比约 7:1 很扁，135deg 的对角线正好把第一个色切成左侧一道窄楔形（纯色区只剩约 16% 面积），而且那道楔子恰落在左上角吊牌底下。Kanade 于是看上去就是”两成黄、八成绿”。

修法：改 165deg 近垂直，两端各留一段纯色平台，让两色各占一条完整横带。

一条更通用的规律：色相距离决定中段灰不灰

这个规律比配色本身更值钱——渐变两端色相距离越远，中段越灰，跟各自的饱和/明度无关。

原理是 CSS 渐变按 sRGB 线性插值，中点 = 各通道简单平均。Haruka 是”蓝 + 黄”，蓝端 H214°、黄端 H48°，隔了接近 166° 近乎互补，两端 R 与 B 各高一头，平均下来必然是 R≈G≈B，量出来 #e8e8d9，肉眼就是灰。Cross 的”梅红 + 橙”只隔 49°，中点就是漂亮的桃色 #f8ddcd，一点问题没有。

⚠ 关键推论：端点怎么调都改不了中点（把黄端一路提到明度 88，中点仍是 #ededdf）。唯一低成本的解法是把纯色平台从 25% 收到 35%（过渡带 50% → 30%，灰带变薄）。想彻底消除得上三色渐变或 in oklch 插值。

🍊 默认橙「发脏」的真正原因（两天里最值钱的一条）

这轮最有价值的收获，是把一个”审美感觉”拆成了可解释的物理原因。

核心洞察：降 HSL 的饱和度只能靠抬 B 通道实现。 橙色相在 ~23° 附近 R 早已顶到 255，想让饱和降下来，只能让 G 和 B 一起涨——而 B 一涨就发灰发土。实测同明度 84 下：饱和 75% 时 B=184，饱和 100% 时 B=173，就这 11 个点换来了那股土气。

所以：

  • 「降饱和到 75% 让色变浅」这条配方 对橙/红这类暖色相是负优化，对黄绿/蓝紫/粉蓝还勉强能用——这也解释了为什么默认橙一直被嫌弃，而 Kanade 那套黄绿没人抱怨
  • 暖色变浅的正解是「保饱和 + 提明度」；色相是唯一能调”甜度”的旋钮：往红偏是珊瑚（最甜）、往黄偏是芒果（最暖）
  • 最终定 **芒果糖果橙 #fddbb9 → #feeddc**（HSL 30° / S94% / L86→93）

同一轮的另一个例外：Aliena 人设本是红白，因白色在亮底不好处理才给设了两个相近的主题色。这轮改回 #f8aaaa → #ffffff**——两色同色相本来做不出双色，红白反而把明度差拉到 18 点，渐变比原来的”粉红→粉红”清楚得多。代价是白端会在白色文章卡上淡出**，卡片下缘只剩那圈 1px 红描边在守边界。

⚠ 还有个同病的漏网：Cross 和 Haruka 的金端——#f5dfb8 / #f5e8b8 正好落在”卡其/芥末”区，同色相同明度只差 25 个点的饱和度。对照 Material amber 100 = #FFECB3，一眼看出差在哪。

顺带做了个语义纠偏：暗色底改完后，bg_dark 字段只剩”亮色主题吊牌字色”一个用途，于是改名 label_fg 并降为单值（原数组第二项早就没有消费者了）。三处必须同步改，漏一处即断链。

🖼️ 正文图片外框：让 alt 兼职第四个岗位（9月23日）

正文插图原先是完全裸的——主题只给了 display:block 和一点下边距，没圆角、没描边、没阴影。

定的是双轨自动分流：

  • 有图注（写了 alt）→ 相纸白框 + 图下小字图注
  • 无图注 → 柔影悬浮，安静地融在排版里

凭什么用 alt 当分流开关？因为它在主题里本来就在兼职三份工作：addPhotoFigcaption() 把它变成图下小字图注、fancybox 的 data-caption 直接读它当放大后的说明、外加无障碍文本。于是写一行字 = 图注 + 放大说明 + 无障碍文本 + 框型开关，四个作用一行搞定。

给读者的规则就一句：想让读者盯着看的图，给它写一行字；随手截的图，不写。 也不额外发明标记语法。

动手前先做了个清理：全库 379 张图里，260 个有 alt 的有 258 个是纯编号（1、3-1、pic-2、还有一批三位数图号）。这些不是图注、是”当时没想到写什么”。清成空 alt（24 个文件 258 处），只留两条真说明。

⚠ 清理脚本必须先剥 fenced code 和行内代码。博客日常使用指南-2.md 里 `![替代文字](图片url)` 是语法示例，第一版正则把它当真图，差点把教程删坏。

实现走 scripts/image-figure.js，after_post_render 优先级 20——必须排在 hexo-asset-image（改 src 为绝对路径）和主题 lazyload（src 换占位图）之后。证据很直观：产出里是 src= "/img/loading.gif" data-lazy-src="…"，src= 后面那个空格就是主题正则留下的痕迹。

⚠⚠ 由此得出一条会绊死人的事实：渲染期 src 一律是 /img/loading.gif，真地址在 data-lazy-src**。所以”排除占位图”这个坑其实不存在（按 src 根本判断不了），但也意味着任何按 src 做判断的逻辑都失效**。

范围要圈死，实测三类容器不能套框：图库 .justified-gallery（62 张，密排贴边，圆角投影会露缝）、按钮组 .btns/.btn（6 张，图是按钮的一部分）、.note 内部（4 张，整块已有底色描边）。排除靠把命中类名的 <div> 整块替换成占位符——而 ⚠ 必须用标签深度配对找闭合，不能用非贪婪正则：note 内部还嵌着 btns，正则会在第一个 </div> 就截断。

四轮迭代，三个真根因

① “阴影看不见”不是太淡，是太散。 阴影可见度 = 压暗量 × 覆盖宽度；0 4px 14px rgba(0,0,0,.1) 用 14px 的模糊把 10% 的暗度摊成了一片雾，峰值极浅。修法是收窄模糊半径（14 → 6px），让阴影贴着下沿成一条暗带——不是加黑。

② box-shadow 是覆盖，不是叠加。 hover 那行没带上原来的黑柔影，一悬停黑影整条消失、只剩一圈橙光，立体感不增反减（越悬停越平）。B站视频卡能用这招，是因为一页最多一两个、且它是真·播放器入口；图片一页十几张，全在喊就是噪音。最终 hover 一律只加深阴影 + 上浮 2px，不带任何颜色。

③ 白底图在白卡上”消失”，是轮廓缺席。 亮色下卡片底、纸底、白底截图三层同色，一对有色差的都没有——同色时那不叫留白，叫没有边界。由此提炼出一个心智模型：

阴影管”图浮起来了”（悬浮感），描边管”图在哪儿”（轮廓感）。 白底图消失是因为轮廓缺席，而阴影只管下方。⚠ 反过来，暗色下黑影基本失效（黑底画黑影等于没画），暗色档的立体感全靠那圈白描边撑着。

⚠⚠ 最狠的一个坑：主题在裁自定义样式的阴影

图片上边缘被截、横宽图左右阴影只剩一条边线、hover 上浮后上边缘被切——三个症状同一个根因：add2.css 有一条全局规则 .fancybox{…overflow:hidden…}，而 fancybox 在客户端会把每张正文图包进 <a class="fancybox">。那个 a 是 flex 列容器：

  • 宽度 = 图片宽度 → 左右零余量，横宽图的左右阴影全被切
  • 上边界 = 图片上沿（img 的下边距只在下方）→ 向上蔓延的阴影被切
  • hover 的 translateY(-2px) 真把图顶出去 → 上边缘真被裁掉

修法是给正文范围放开裁剪、图库保持 hidden（它靠这层裁 2px 圆角）。连锁收获：上一轮”白底图和卡片融为一体”在真实站点上比预览里严重得多——那圈本该让白底图显形的 1px 描边，一直是被这个 a 裁掉的。

第四轮的教训是判据定错了。 有一篇教程的 6.png 没套上框，查下来是”认为段落里除图还有文字 = 行内配图”这条规则误伤。可主题给 #article-container img 的 display:block 是全局的——段落里的普通图本来就会独占一行，根本撑不断句子；唯一会被撑断的是带 .inline-img 的图。所以这条规则是基于错误前提的重复保护。

铁律：**行内图的唯一判据是 class 含 .inline-img**。别拿”段落里还有文字”当判据——那条判断曾让 6 张正常插图漏框。

🧹 内嵌 HTML 治理：34 + 24 + 5 + 14

翻 md 的时候总撞见一长串手写 HTML，”还得想一下这是干嘛的”。于是先盘点：全库 35 篇含真 HTML，346 个标签，全是自定义组件加零散标记。

⚠ 两个扫描纪律：① 标签正则必须收紧成 /<\/?([a-zA-Z][a-zA-Z0-9-]*)(?:\s[^>]*)?\/?>/——用 \b 收尾会把 C++ 泛型 <u,v>、<T,N> 误判成 HTML（第一版因此误报 4 处）；② 扫 md 之前先剥代码块和行内代码。

迁移结果（21 篇）：

  • 警告框 tip warning ×34 → {% note warning flat %}
  • 纸夹便签 snote paperclip light ×24 → {% note fa-paperclip flat %}
  • 下载卡 snote download yellow ×5 → {% btn url, text, fas fa-download, block %}
  • </br> ×14 → 删除

⚠ </br> 根本是个错误写法：产出 HTML 里既没有 </br> 也不见转义后的 &lt;/br&gt;，被渲染环节静默丢弃。它们又都夹在空行之间，所以删掉视觉零变化，纯白写了一场。

标签参数机制，试一次错一次

{% note %} 的参数解析很挑：

  • lastArgs 是 flat / modern / simple / disabled 时不自动补 style 类
  • args[args.length-2] 必须以 fa 开头才被识别为图标，且会替换成字符串 icon 当 class
  • ⚠ 所以 {% note paperclip flat %} 不识别（不以 fa 开头）

⚠⚠ 而且 note 内容会走二次 markdown 渲染（Hexo 默认 breaks:true + smartypants）：多行纯文本会变成每行一个 <br>**；- 和 1. 变成真列表；半角引号会被 smartypants 转成弯引号**。前两条是改善，第三条是意外——('\n') 变成了 (‘\n’)。

一个必须写下来的权威事实

{% note %} 的 type 参数在本站实际无效：danger 和 success 渲染出来一字不差——主题 note.styl 里的 &.{$type} 配色被 custom.css 的默认基线整段覆盖了。结论：迁移后所有非角色 note 都是同一张糖果芒果橙卡片，”警告/便签”想靠 type 区分颜色是做不到的。

顺带一句：那 5 个下载卡最后既没用引用块、也没用链接卡片，两个都是查了真实计算样式才否掉的——

  • 引用块在 OC 专栏正承担「角色语录」（同页就有 > 愿你太阳色的羽翼…），下载块改用 > 会与语录同脸，读者分不清”角色在说话”还是”这是下载”
  • 链接卡片会原样印出 URL（.link-card p.url），实测 url 字号 14.25px 还比 title 的 11.5px 大；配上那串 110 字符的中文路径编码 URL，整张卡就是一条巨长不可读串

按钮则有个已知的遗留：亮色底 --btn-bg = #ffba88 配白字，对比度约 1.7:1，偏低；这是全站按钮统一的色板，嫌糊可以加字重或加深底色，暂未动。

📺 B站视频外框：天线小电视（9月23日）

这条差点被漏记——它只留在 custom.css 的一段注释里。

原先 B站嵌入就是个光秃秃的 iframe，连圆角都没有。分两轮”试衣间”出的方案：

  • 第一轮四个候选：简约细边框 / 仿 B 站标题栏（粉底 + 「B」徽标 + BV 号）/ 品牌粉发光框 / 深色磨砂相框

  • 试完的结论是：不该用 B站粉。博客的主色语义槽是亮橙/暗砖红，硬塞一个粉色进来，等于在自家色板里开天窗

  • 第二轮改成全部走站点语义槽（--color-accent / --color-border / --color-shadow），亮暗自动切换，出四个变体：天线小电视 / 顶边贴边双线 / 电视信号条 / 纯换色发光框（上一轮的对照基准）

最终定变体 1「天线小电视」：两根 V 形天线从框顶伸出、中间一个圆点当底座。

一个容器不能同时当相框和视口

这轮最实在的一条经验。天线是从框外伸出去的（top: -20px），所以外层 .bili-video **绝对不能 overflow:hidden**——那等于自己把天线裁掉。可视频又需要裁圆角。

解法是职责拆开：外层只管相框、放开裁剪；圆角交给内层 .bili-video-inner 承担（overflow:hidden + 9px 圆角 + 16:9）。

另外两个细节：

  • 三根部件（两根天线 + 一个圆点）里必须有一根走真实元素——一个元素只有 ::before / ::after 两个伪元素可用，所以圆点做成了 <span class="bili-antenna-dot">
  • 外层 margin-top: 30px 是特意给框外天线留的位置，不写的话天线会直接压到上一段文字上

顺带把 scripts/bilibili.js 里那一整串内联样式全删了，结构改成 .bili-video > (.bili-antenna-dot + .bili-video-inner > iframe)，样式收进 CSS——结构归脚本、外观归样式表，跟这两天的整体思路一致。（audio 音频条这轮没动，仍是原来的内联样式。）

🔬 验证工具链升级：只信真实页面

这两天验证次数极多，工具也跟着进了一步。核心是 _shot.js：起一个临时本地静态服务器服务 public/，让无头 Edge 访问 http://127.0.0.1/... 并且注入诊断脚本（真实 hexo 页面直接 file:// 抓是白屏——绝对路径 CSS 全 404）。

它有两个探针：

  • 读任意选择器的 computed style
  • 反查规则来源：遍历 document.styleSheets，用 el.matches(rule.selectorText) 找出到底哪条规则在设 overflow/display —— 这次就是靠它锁定了 add2.css 的 .fancybox

三条踩出来的纪律：

⚠ 判最终观感要用静态快照，别用动态读值。 用 setAttribute 切主题后立刻读 computed style，读到的是颜色 transition 的起始值——本小姐曾因此以为”深灰压深灰不可读”，静态快照里文字其实是浅色、清清楚楚。

⚠⚠ 自制预览页已经失真三次。 缺 fancybox 那层 <a class="fancybox">、缺 add2.css、.tip 渲染与真实站不符……凡判断组件真实外观，一律以真实页面的 computed style 或静态快照为准。

⚠ 改渲染期脚本（scripts/）先跑桩测试，别急着花 4 分钟全量重建。桩的写法很省事：global.hexo = {extend:{filter:{register:(n,f)=>{fn=f}}}} 然后 require 脚本，直接拿到回调喂样例。
