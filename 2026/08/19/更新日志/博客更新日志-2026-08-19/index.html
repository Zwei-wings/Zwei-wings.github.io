博客更新日志 — 2026年8月19日

今天本小姐化身”细节强迫症患者”，一口气打磨了五个地方：签到日历的计数逻辑、播放器的记忆能力、上一篇/下一篇的排序、相关推荐的推荐策略、还有引用块的颜值。都是那种”不改也能用，改了才叫舒服”的小事。但博客的质感，不就是这些小事堆出来的吗？

📅 签到日历：细读升级为「篇数」

从”读过”到”读了几篇”

之前签到日历里的「细读」是个布尔值——要么今天读过，要么没读过。但本小姐越想越觉得不对劲：更文是按篇数统计的，细读凭什么只算”来没来过”？凭什么一天细读 3 篇和细读 1 篇，在日历上长一个样？

不公平。于是把「细读」从布尔升级成了计数——同一天在 read_dates 里重复写几次，就记几篇。数据语义直接变了：

这个改动像涟漪一样波及了整条链路：周进度条的及格线 5、满分 7 现在按篇算，读超 7 篇会触发溢出条（金色 + 溢出，仪式感拉满）；热力图和连续打卡的判定也改成 read > 0。不过连续打卡的”连续”还是按天算——毕竟”连续 30 天”比”连续 30 篇”更像人话。

顺手修了个偷懒的文案

改着改着发现正文页双轨进度条的刻度标签是硬编码的——「日更达成!」「写作力溢出!」「日更 7」。更文那条轨这么写没毛病，可细读轨也顶着一串”日更”？细读跟”日更”有半毛钱关系吗？

于是按轨道区分了文案：

  • 更文轨（p）：「日更达成! / 写作力溢出! / 日更 N」
  • 细读轨（r）：「读满达成! / 阅读力溢出! / 读满 N」

一个 isReadTrack = (cls === 'r') 的三元判断解决。之前就是偷懒，本小姐认了。

🎵 音乐播放器：学会「记住」了

播放器之前有个很憨的毛病：调了半天音量、切好了循环模式，结果一刷新页面（F5），全给你打回原形。辛辛苦苦调到 40% 音量，一刷新变回 100%，耳朵直接遭殃。

于是给它加了记忆功能——用 localStorage 存两样东西：

  • nav-music-volume：音量（0–1 浮点）
  • nav-music-loop：循环模式索引（0–3 整数）

音量滑块 input 时存、循环按钮点击时存；初始化时读出来恢复。静音状态明确不记——毕竟静音大概率是”临时不想听”，不是”永久偏好”。这个分寸，本小姐拿捏得死死的。

有个点要说明白：localStorage 存在本机浏览器里，换设备、清缓存都会失效。而且 PJAX 切页时 navAp 不重建、音量内存里就保持着，所以 localStorage 主要是在整页刷新（F5）那一刻起作用。别指望它跨设备同步，它不是云，本小姐也不是。

📖 上一篇/下一篇：让小说章节归位

这是今天最有含金量的一块。

问题：章节乱串门

Hexo 默认的上一篇/下一篇是全局按 date 倒序排的（源码 node_modules/hexo/lib/plugins/generator/post.js 第 4 行，sort('-date')）。结果就是：小说、南院、更新日志、学习笔记全混在一起。你点开小说第 5 章，底部的「下一篇」可能蹦到学习笔记去——上一秒还在看主角生死攸关，下一秒让你复习 C++ 指针。出戏到离谱。

方案：系列内排序

新建 scripts/post-nav-order.js，注册一个 generator series_post_order，在文章生成后重排 prev/next。关键认知：scripts 里的 generator 会在内置 post generator 之后执行，所以能覆盖它的排序；return [] 表示不生成任何新页面，纯做排序。

序号提取的优先级（命中即停）：

  1. **文件名末尾 -N**（但要排除 -YYYY-MM-DD 这种日期尾巴）
  2. 标题「第 N 章」 → 章节号，系列用 category 唯一化
  3. 标题末尾 -N
  4. 都没命中 → 不分组，按 date 倒序

串联逻辑：系列内按序号升序（prev = 上一章，next = 下一章），系列之间、未分组之间断开——不会再串门了。配合主题的 post_pagination: 1，「上一篇」= prev、「下一篇」= next，方向也对得上。

几个决策的来龙去脉

  • 为什么不改标题？ 因为 permalink = :year/:month/:day/:title/，改 title 会改 URL，风险太高。最终选了文件名优先，零改动文章本身。
  • 更新日志的特殊性：title「博客更新日志-N」是序号，但 filename 是「博客更新日志-YYYY-MM-DD」是日期。靠日期排除正则兜住，走 title 判断，完美。
  • C++ 学习笔记：标题前缀乱得很（「C++基础」「c++拓展」，还撞号），但文件名「c++学习-1~14」很规范。文件名优先自动解决，一篇都不用改。
  • 第 8/9 章标题缺空格（「第8章」而不是「第 8 章」），正则 第\s*(\d+)\s*章 容忍了。本小姐的正则，向来这么通情达理。

🔗 相关推荐：三缺一，干脆不推荐

问题：4 个挤一排，多出一个

主题默认的相关推荐 limit: 4，而排版是一排 3 个（CSS 写死 width: calc(33.333% - 6px)）。于是每次都是 3 + 1，多出来的那一个孤零零挂第二排，像最后排挤不进大合照的人。丑。

方案：覆盖主题 helper

Butterfly 自带 related_posts helper（按共享标签数量降序推荐）。本小姐新建 scripts/related-post.js，注册同名 helper把它覆盖掉，策略改成：

  1. 用当前文章的 prev/next 建立”排除集合”——上一篇和下一篇是读者刚刚要看的，不该再出现在推荐里
  2. 排除后不足 3 篇就直接不显示（return 空字符串），宁缺毋滥
  3. 够了就取前 3 篇，HTML 结构和类名跟主题一致，复用现成的样式

推荐算法（共享标签权重）本身不变，只改”给谁看、看几个”。验证结果：小说第 2 章推荐了第 18/17/16 章，不含上一篇（第 1 章）和下一篇（第 3 章）。完美。

踩坑：主题脚本会”后手覆盖”

这个坑值得大书特书——第一次改完，压根没生效。

查了半天才发现一个反直觉的事实：主题的 scripts 和站点的 scripts 是并发加载的（hexo/lib/hexo/load_plugins.js 用 bluebird .map，默认 concurrency=0 即无限并发），根本不是“站点后加载”。主题有 30 多个文件，比站点的 4 个文件慢，结果就是主题的 helper 后注册、把站点脚本覆盖了。

这个认知简直颠覆三观：你以为你在”覆盖主题”，结果主题反手把你盖了。

修复：把 helper 注册包进 hexo.extend.filter.register('after_init', ...)。after_init 在所有脚本加载完（load_plugins 结束）才执行，保证是最后那个覆盖者。这招记下来，以后凡是要覆盖主题 helper/filter 的，都得走 after_init。

💬 引用块：从”蓝色冷脸”到”暖橙卡片”

最后一个纯颜值项。默认的 blockquote 是「蓝色竖线 + 淡蓝底 + 灰蓝字」（#49B1F5），跟博客的暖橙主题（#ff9a5c）放一起，就像一个冷脸客人闯进了暖色调的客厅。突兀。

选了「柔卡片」风格，在 inject.head 里内联覆盖（浅色 + 暗色两套）：

  • 橙边框 rgba(255,154,92,.28) + 左侧 3px 橙线 #ff9a5c
  • 暖白底 #fdf9f5 + 圆角 8px + 文字 #7a6a5a
  • 暗色模式：淡橙透明底 + 白 0.72 文字

现在引用块总算跟整站一个温度了。已 hexo g 验证注入成功。

📋 验证清单

  • hexo g 零报错
  • 细读计数：同一天写 3 次 = 3 篇，周进度条按篇计算
  • 细读轨文案区分（读满达成 / 阅读力溢出 / 读满 N）
  • 播放器 F5 刷新后音量、循环模式恢复
  • 小说章节 prev/next 系列内正确排序，不再串门
  • 相关推荐最多 3 篇，排除上下篇，不足 3 篇不显示
  • 引用块暖橙卡片样式，明暗两套正常
